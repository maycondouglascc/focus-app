## Summary

Phase F2 passes all Gate 2 criteria. The retained-mode native UI toolkit (`Tree` on `taffy`, Direct2D/DirectWrite over DirectComposition, unified `WM_POINTER*` input, `FocusModel`, `accesskit_windows` UIA bridge, top-level `WS_POPUP` windows, system preferences/high-contrast/Mica, and the closed F3-scoped widget catalog) is complete and verified.

Two targeted runtime optimizations were made and documented before closing F2:

1. **MSVC `/DELAYLOAD` on `focus.exe` (`win32/build.rs`)**: Without delay-loading, static `.idata` imports from `windows` / `accesskit_windows` mapped `d3d11.dll`, `d2d1.dll`, `dcomp.dll`, `dwrite.dll`, `UIAutomationCore.dll`, and `dwmapi.dll` into the F0 background monitor before any window ever opened (~15.14 MB WS). Delay-loading those 6 DLLs keeps closed-window monitor usage at **5.59 MB private / 13.30 MB working set / 0% idle CPU**.
2. **Prefer `D3D_DRIVER_TYPE_WARP` over `D3D_DRIVER_TYPE_HARDWARE` (`win32/src/ui/render.rs`)**: Measuring open-window Working Set with hardware Intel Iris Xe D3D11 (`igc64.dll` + `igd10um64xe.DLL`) consumed **71.65 MB WS on the bare F1 baseline** and **72.96–74.05 MB WS** with F2 widgets (exceeding the `< 60 MB` open-window Working Set budget) and ~246–262 ms cold first frame. Preferring `D3D_DRIVER_TYPE_WARP` with `D3D11_CREATE_DEVICE_SINGLETHREADED` keeps DirectComposition, Mica (`DWMWA_SYSTEMBACKDROP_TYPE`), rounded corners, and 60fps retained redraws intact while reducing open-window Working Set to **40.49 MB** (bare shell) / **44.25 MB** (full widget gallery) and reducing closed-window post-open `--ui-cycle 50` private memory to **12.35 MB** (`+0.28 MB` growth). Hardware fallback remains second in the driver list.

## Environment / Contention Observations

- Three pre-existing `focus.exe` test processes from an earlier exploratory run (`PIDs 2076, 14580, 54176`) remained hung in kernel threads burning CPU across 3 logical cores on the host during measurements. Their lock on `win32/target/release/focus.exe` was cleared safely by renaming the stale binary prior to `check.ps1 -Release`.
- Because `DefWindowProcW(WM_ACTIVATE)` incurred a ~2.0s synchronous activation delay from the 3rd top-level `ShowWindow(SW_SHOW)` onward on this desktop session (even on the bare F1 baseline), `focus.exe --ui-cycle 50` (100 warm-up + 50 measured cycles) took `308.7s` total wall time (vs `105.2s` for the 50 measured cycles), completing cleanly with `OK`. Cold first-frame latency also reflects full process creation plus first-load resolution of delay-loaded DLLs under endpoint security scanning (`SophosED.dll`) and background CPU contention.
